04_business_semanticsStep 4

4Business semantics

The dashboard and Genie work — but every number was re-derived in each tile and each answer. That's how "return rate" ends up meaning three different things. This step adds the trusted, governed definition once, so everything reads the same number — and it's the foundation that lets Genie One answer any business user's question with confidence. → Back to the introduction

How the semantics stack fits together

Your data already holds the answers — but the meaning is scattered across dashboards, SQL, spreadsheets and people's heads. Unity Catalog puts a governed business semantics layer directly on the data, so AI resolves the right definition instead of guessing from raw tables. Four layers, each solving one problem:

Raw data
Facts & events — orders, returns, production lots
Metric View
Makes the numbers right. Governed KPIs + dimensions, defined once — "return_rate = returns ÷ orders"
Pages & Domains
Make the language right. Authoritative definitions of terms & concepts (Pages), organized by business area (Domains) — "what counts as an anomaly"
Genie Ontology
Makes the context connected. Links your modeled definitions with knowledge inferred from dashboards, queries & agents; ranks sources by authority
Genie One
Makes it accessible to everyone. One front door: business users ask in plain English, grounded in the governed context — "why did returns spike in France?"

The strategy: model the head, infer the tail — hand-model your few most important KPIs and terms, and let the ontology infer the rest from what you've already built. We'll start that here with one metric view.

1/ Create a metric view — start simple

A metric view is the governed semantic layer: define your dimensions (how you slice) and measures (what you count) once, and the dashboard, Genie, and any SQL query all read the same MEASURE(...) — no drift. Start with the core measures:

Ask Genie Code

Create a metric view called mv_returns over gold_daily_summary, with dimensions date (from the summary_date column), region, category, and source (CASE WHEN is_bad_lot THEN 'Affected lot' ELSE 'Everyday' END), and these measures: total_revenue = SUM(revenue_usd), total_refunds = SUM(returns_usd), order_count = SUM(order_count), return_count = SUM(return_count). Then query a couple of measures to confirm it works.

💡 The source dimension is what lets a business user ask Genie "what's the return rate on the affected lot versus everything else?" without knowing the is_bad_lot column exists.

2/ Extend it — ratios + business language

Now make it production-grade. Add the ratio measures (the ones people compute wrong) and the agent metadata — synonyms, display names, formatting — that teaches Genie the business language, so someone asking for "refund rate" or "% returned" lands on the right measure.

Ask Genie Code

Extend mv_returns:

• add return_rate = SUM(return_count) / NULLIF(SUM(order_count), 0) and refund_rate = SUM(returns_usd) / NULLIF(SUM(revenue_usd), 0). Write ratios this way — not MEASURE(a)/MEASURE(b) — so they stay correct under any filter and never divide by zero.
• give each measure a friendly display name and synonyms (e.g. return_rate → "return %", "returns rate"; total_refunds → "refunds", "refund dollars"), and set formatting (currency for dollars, percent for rates).

Then query MEASURE(return_rate) by week to confirm.

✅ Confirm: the spike week's return_rate should be well above the baseline — and asking Genie for "return %" now resolves to this measure.

💡 Beyond metric views: in a real rollout you'd add Pages (authoritative definitions for terms like "anomaly" or "active customer" — Genie One cites them), organize assets into Domains, and certify the trusted ones. Genie Ontology then blends all of it with what it infers from your dashboards and queries — so Genie One answers from authoritative context, not guesswork.

Prereq: 2. Build the pipeline finished, so the gold tables exist. As before, each step is a prompt for Genie Code.

1/ Govern PII with ABAC — tag once, one policy covers everything

ABAC (Attribute-Based Access Control) is the modern, tag-driven model: you tag sensitive columns, write one CREATE POLICY on the schema that matches those tags, and it auto-applies to every column carrying the tag — today and every future table. That's the story per-table SET MASK can't tell.

1a — Tag the sensitive columns.

Ask the Assistant

Tag the PII columns on the returns gold table — the customer id and the geo columns — with a governance tag.

1b — Write the masking function + the ABAC policy (the load-bearing part — one schema-level policy driven by the tag, not per-table masks):

Ask the Assistant

Create a redaction function, then a tag-driven ABAC column-mask policy on the schema that masks every column tagged as PII for everyone except the ops group. Add a row-filter policy too, so regional analysts only see their own region.

1c — Verify by persona (the payoff):

Ask the Assistant

Show me the returns table as the ops group vs a regular analyst — ops sees raw geo, the analyst sees it masked, aggregates unchanged.

1d — Prove the ABAC win: one tag, instant coverage. Tag a column on a different table and watch the existing policy pick it up with zero new DDL:

Ask the Assistant

Tag city on silver_returns as PII with the same tag, then show me that column as the analyst — it should already be masked by the policy I wrote in 1b, without creating any new policy.

🛑 Use silver_returns.city — do NOT tag facility on silver_production_lots. A factory site isn't personal data, so the tag would be wrong on its face — and that column holds Lyon-France, the single value the entire demo builds toward. Mask it and Genie's punchline comes back REDACTED for every non-admin persona, including the analyst persona you just created. The demo breaks and it looks like the platform's fault.

1e — Untag it. This step is not optional.

The 1d tag exists only to demonstrate propagation. Leave it in place and you've permanently masked a column for every analyst who opens this workspace later.

Ask the Assistant

Remove the PII tag I just added to silver_returns.city, then confirm the analyst can read the column again.

✅ Confirm: the analyst sees real city names on silver_returns again, and silver_production_lots.facility still returns Lyon-France — not REDACTED — for every persona. Run this before you move on:

SELECT DISTINCT facility FROM silver_production_lots WHERE facility LIKE 'Lyon%'

💡 Gotchas to hand Genie Code if it stumbles: the mask function's return type must match the column type; one row filter per table, one mask per column. You can't both mask and row-filter on the same column — that's why region stays visible. The exact policy grammar lives in specifications/02-uc-governance.md.

2/ Run data classification

Let Unity Catalog scan and classify the schema so PII is found automatically — not just where you remembered to tag it.

Ask the Assistant

Run data classification across the schema, then show me what it flagged as sensitive — emails, names, locations — and how to review and accept the suggestions. Show me the proposals; don't apply them yet.

3/ Review the proposals before you accept them ⚠️

This is the step people skip, and it's the one that matters. The scanner infers semantics from column names and sampled values, and it gets things wrong. On this very dataset it has proposed:

ColumnProposedWhy it's wrong
customer_lat, customer_lngpii = ssnCoordinates are not a national ID. Accepting this null-masks the columns — and kills the returns map on your Operations page.
customer_idpii = addressA surrogate key is not an address. Masking it breaks drill-downs and joins.
facilitypii = addressA manufacturing site is not personal data — and this is the Lyon-France punchline.

So: read every proposal and reject the wrong ones.

Ask the Assistant

For each classification proposal, tell me the column, the proposed tag, and a sample value. I'll tell you which to accept. Reject anything where the tag doesn't actually describe the data — in particular don't classify latitude or longitude as a national-ID type, don't classify a surrogate key as an address, and don't classify a manufacturing facility as personal data.

✅ Confirm: after accepting, re-run your persona check from 1c. Coordinates should still render on the map for ops, customer_id should still join, and facility should still read Lyon-France. If any of those broke, a proposal you accepted is driving a mask it shouldn't.

💡 The lesson to say out loud in front of a customer: auto-classification is a discovery tool, not an authority. It finds candidates at a scale no human can; a human still decides what each one means. A governance demo that accepts every suggestion unreviewed teaches precisely the wrong habit.

✅ Governed

ABAC + reviewed classification keep PII safe across every current and future table — without masking the columns the business actually needs.

6ML — the hidden-premium classifier

The business twist: CS hand-tagged about 650 customers premium / not_premium, but most are untagged — not non-premium, just never reviewed. A model trained on the labeled ones finds the hidden premiums a WHERE premium_status='premium' query can't. → Back to the introduction

Prereq: 2. Build the pipeline is built. This page adds a Unity Catalog feature table, then trains + batch-scores from it — each step a prompt for the Assistant ().

1/ Build the feature table

The classifier trains on per-customer behavior. Store it as a Unity Catalog feature table: one row per customer, keyed by customer_id, so training and scoring read the exact same features.

Ask the Assistant

Create a Unity Catalog feature table gold_customer_features with FeatureEngineeringClient().create_table, primary key customer_id: one row per customer with spend, orders, tenure, return rate, recency and loyalty tier. Keep the premium_status label out of it. Show me the row count.

✅ Confirm: the table shows up under Features in Catalog Explorer, with customer_id as its primary key.

2/ Train + register the classifier

The training set is just customer_id + label for the ~650 tagged customers. The feature table fills in the rest.

Ask the Assistant

Train a premium-status classifier on the labeled customers: take customer_id + premium_status from the customers data, look the features up from gold_customer_features with FeatureLookup + fe.create_training_set, track it in MLflow, and log it with fe.log_model(training_set=...) to Unity Catalog — wrap any encoding + the model in one pyfunc that returns the premium probability. Then set the prod alias on that version with MlflowClient().set_registered_model_alias(...) and read it back.

✅ Confirm: registering is not the same as aliasing — the Assistant often skips the second. Check it:

Ask the Assistant

Show me the aliases on the registered model, and the feature table it was trained from.

No alias → the next step's models:/…@prod lookup fails. The MLflow run should show a sensible AUC, and the model's lineage should point at gold_customer_features.

3/ Score everyone → find the hidden premiums

Ask the Assistant

Batch-score every customer with fe.score_batch on the prod model (result_type="double") — pass only customer_id, the features are looked up for you — into customer_premium_predictions: probability, predicted flag, CS label, and a final tier that's premium if either the model or CS says so. Then check: among the bad-lot customers, how many come out premium?

✅ Confirm — check the shape, not an absolute count. Row counts here scale with the generated data, so verify the relationship instead:

Ask the Assistant

Show me a 2x2 of CS label (premium / not_premium / unlabeled) against the model's prediction, with counts.

Three things should be true:

  1. There are model-found premiums — unlabeled customers the model flags premium. These are the hidden ones a WHERE premium_status='premium' filter can never return. That's the punchline.
  2. The model mostly agrees with CS where CS actually labeled — the diagonal (premium→premium, not_premium→not_premium) should dominate the off-diagonal.
  3. It is not flagging the majority of the unlabeled pool. If well over half of the unlabeled customers come back premium, the model has learned "say yes" — the labeled set is too small or too imbalanced to be useful. Say so: "the model predicts premium for most unlabeled customers — check class balance and recalibrate the threshold." A classifier that calls everyone premium tells the opposite of the story we're here to tell.

4/ Let Genie tell the story

Ask the Assistant

Attach the predictions table to the Genie space, then let me ask it: 'how many premium customers did the model find that CS never tagged?'

✅ Confirm: Genie answers with the count of model-found premiums (predicted premium, no CS label) — the hidden premiums a WHERE premium_status='premium' query would miss.
