# Stage 03′ — Build a Workshop (Genie Code)

Run this **instead of `03.1-build.md`** when the project is in **workshop mode**
(the home page's "Genie Code workshop" tab; the opening prompt says so). You do
NOT provision Databricks resources. You produce a set of **clean Databricks
notebooks** whose cells are Genie Code prompts the SA pastes into the Databricks
Assistant to build the demo **live, one step at a time**, then **load them into
the workspace** (the workshop's "Build" step) — and the whole package is also
downloadable as a zip to hand to a customer.

All files go in the project folder.

## The reference to pattern-match

`references/example-luxebeauty-workshop/` is the worked example — read it first.
Mirror its shape, adapting the story/data/columns to THIS project's specs:

```
notebooks/00_introduction.py         # HUB: platform + story intro, links to every step, priming prompt
notebooks/01_setup_and_explore.py    # run data-gen → Volume, explore
notebooks/02_build_pipeline.py       # silver → gold, one table at a time + AI functions
notebooks/03_dashboard_and_genie.py  # the dashboard + Genie space (Genie Code prompts)
notebooks/04_governance.py           # metric view + ABAC + data classification (if in scope)
notebooks/05_ml.py                   # train + batch-score the classifier (if ml in scope)
data_generation/generate_data.py     # writes raw_* parquet → UC Volume /raw_data/<dataset>/
CONTEXT.md                           # the primer the notebooks' first cell points the Assistant at
specifications/{01-lakeflow,04-ai-bi}.md  # the target table/column + widget/Genie contract
```

**No pipeline/SDP SQL is shipped.** The whole point of the workshop is that Genie
Code writes the silver/gold SQL live from the notebook prompts — so the reference
carries NO `pipeline/*.sql`. The target contract (table + column names) lives in
`CONTEXT.md` + `specifications/01-lakeflow.md`.

(`README.md` + `resources.json` + `specifications/` you already wrote in stages 1–2.)

## Behavior rules

- **Notebooks are Databricks notebook-source `.py`** — `# Databricks notebook source`
  header, `# COMMAND ----------` cell separators, `# MAGIC %md` markdown cells.
  They import into a workspace and render with the Assistant panel on the right.
  **Use `%md-sandbox` (not `%md`) for any cell with advanced HTML** — floated
  `<img>`, `style="float:right"`, styled divs. Plain `%md` strips that styling;
  `%md-sandbox` renders it in a sandboxed iframe (this is how dbdemos does its
  floated banner images). Plain prose cells stay `%md`.
- **The cells are PROMPTS, not code.** Each build step is a `%md` cell telling the
  SA what to paste into the Assistant (✨). The Assistant reads `CONTEXT.md` and
  writes the SQL/Python; the SA reviews + runs it. Keep prompts one-step-at-a-time.
- **Raw data lands as parquet FILES in a UC Volume** (`/Volumes/{cat}/{schema}/raw_data/<dataset>/`)
  — the bronze landing zone. Silver reads it via `read_files()`; **no bronze
  pass-through**. The data-gen script writes ONLY the raw datasets (it does NOT
  build silver/gold — the SA builds those live).
- **CONTEXT.md is the Assistant's ground truth** — the story, the table +
  column contracts, the medallion targets, the Genie config. The first notebook
  cell points the Assistant at it + the specs. It's the contract Genie Code
  converges on — the workshop ships NO SDP SQL.
- **Prompts read like a human building a real pipeline** — natural, high-level
  intent ("build the cleaned returns table joining products + customers, score
  sentiment with ai_classify"), NOT a schema dump or "see CONTEXT.md for the
  columns". The grounding (exact names) lives in CONTEXT.md up front; the
  per-step prompts stay conversational and realistic.
- **No resource provisioning, no DAB.** The deliverable is the downloadable
  package. Leave `resources.json.created_resources` with `<built-live-in-the-workshop>`
  placeholders (see the reference's resources.json).

## The recipe

1. **Read the reference** (`references/example-luxebeauty-workshop/`) end to end —
   notebooks, CONTEXT.md, the data-gen. That's the template.
2. **Adapt `data_generation/generate_data.py`** to this project's data spec
   (`specifications/01-lakeflow.md`): same volume-writing shape (`_save` → parquet
   to `/Volumes/{cat}/{schema}/raw_data/<dataset>/`, `CREATE VOLUME IF NOT EXISTS`),
   this demo's tables/columns/story.
3. **Write `CONTEXT.md`** — the story + the table/column contracts + the
   medallion targets + the Genie attach list, instruction text, and sample
   questions. This is the single most important file for making Genie Code
   effective — and it's the ONLY place the silver/gold shape is written down
   (no SDP SQL ships; Genie Code writes it live from the prompts).
5. **Write the notebooks** — start with `00_introduction` (the HUB: platform +
   story intro, a linked table of the steps, and the one-time priming prompt —
   NO build prompts), then the step notebooks whose capabilities the demo needs:
   `01_setup_and_explore`, `02_build_pipeline` (silver/gold + AI functions),
   `03_dashboard_and_genie`, and — when in scope — `04_governance` (metric view +
   ABAC + classification) and `05_ml` (train + batch-score). Each step notebook
   opens with a banner (emoji-number title + a `[Back to the introduction]($./00_introduction)`
   link), uses `N/` slash sub-headers, and ends with a `▶️ Next: [...]($./NN_next)`
   link. Prompts read like a human building (see the tone rule above); the exact
   names live in `CONTEXT.md` + the specs.
6. **Load everything into the workspace** — the workshop's equivalent of the
   Build step. **`resources.json.created_resources` is the single source of truth
   for the paths** — set them FIRST, then use them for the upload + data-gen so
   the notebooks, CONTEXT.md, and the loaded location all agree:
   - `catalog`, `schema` — the target (from the project's default catalog/schema).
   - `raw_volume` — `/Volumes/{catalog}/{schema}/raw_data` (where data-gen writes
     and the silver `read_files()` reads — they MUST match).
   - `workspace_folder` — `/Workspace/Users/{me}/{demo-slug}_workshop` (where the
     notebooks load).

   Then upload + generate, reading those values (no ad-hoc paths):
   ```bash
   WS=$(jq -r .created_resources.workspace_folder PROJECT/resources.json)
   databricks workspace mkdirs "$WS"
   for f in PROJECT/notebooks/*.py; do
     nb="$(basename "$f" .py)"
     databricks workspace import "$WS/$nb" --file "$f" \
       --format SOURCE --language PYTHON --overwrite
   done
   # Ship CONTEXT.md next to the notebooks so the Assistant can read it.
   databricks workspace import "$WS/CONTEXT.md" --file PROJECT/CONTEXT.md --format RAW --overwrite
   # Land the data in the Volume (raw_volume above) so the notebooks have data.
   DEMO_CATALOG=<catalog> DEMO_SCHEMA=<schema> python3 PROJECT/data_generation/generate_data.py
   ```
   (`PROJECT/deploy.sh` in the reference does exactly this end-to-end — keep its
   paths in step with `resources.json`.)
7. **Tell the user** the workshop is loaded — the workspace folder link + volume
   path — and how it runs (open `00_introduction`, follow its links, paste each
   step's prompt into the Assistant ✨). Also note the whole package can be
   downloaded as a zip to hand to a customer.

## Coherence checks

- Every table/column a notebook prompt names exists in the data-gen output or the
  CONTEXT.md contract.
- The volume subdir names in the data-gen `_save` mapping match the `read_files()`
  paths the silver prompts use (strip the `raw_` prefix: `raw_returns` → `returns`).
- The Genie punchline works: the lot's `incident_summary` is reachable as a
  queryable table (expose `silver_production_lots` if raw is volume-only).
- The story holds end-to-end (spike in the past, affected lot dominates, incident
  note on the lot) — same bar as a normal build.
